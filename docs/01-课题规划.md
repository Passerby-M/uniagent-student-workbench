# UniAgent（大学生综合工作台）课题规划

## 1. 课题名称

**基于 Agent 的大学生综合工作台系统的设计与实现**

英文暂定：Design and Implementation of an Agent-Based Integrated Workbench for University Students。

## 2. 研究定位

面向大学生校园事务入口分散、制度理解困难、材料反复补交、流程状态不透明等问题，设计一个由 Agent 提供自然语言统一入口、由工作流引擎保障业务可靠流转的综合工作台。

学生可以直接表达目标，例如“我要请三天假”“我能申请哪类奖学金”“帮我看看材料还缺什么”。Agent 负责识别意图、查询制度、收集信息、检查材料、生成表单草稿和解释进度；Flowable 负责提交后的任务分配、条件分支、人工审批、状态变更和操作留痕。

系统不把 Agent 设计成自主审批者。涉及正式提交、审批决定、敏感信息使用和办结归档的动作，必须经过用户确认或确定性规则校验。

## 3. 为什么从教师调整为学生

学生场景能显著增加 Agent 的有效接入点：

- 学生通常不熟悉部门边界和制度术语，更需要意图识别与事项导航；
- 奖助学金、请假、证明、活动等事项规则多，适合制度检索与资格解释；
- 不同事项重复填写个人、院系和学籍信息，适合对话式信息收集和表单草拟；
- 申请材料多且容易遗漏，适合规则校验与 Agent 语义预审结合；
- 流程节点多，适合自然语言进度解释和下一步提醒；
- 相似历史问题多，适合带引用的校园制度问答。

提升的是 Agent 接入的自然性和可评价性，不代表让 Agent 获得更高决策权限。学生数据涉及身份、学籍、奖助和健康等信息，仍需坚持最小数据访问和人工确认。

## 4. 研究主线

论文由原来的“工作流主体、Agent 辅助”调整为：

> Agent 负责理解、协助和编排用户任务，工作流负责可靠、可控、可审计地执行正式业务。

研究重点不是实现一个通用聊天机器人，而是研究 Agent 如何在受控边界内连接制度知识、学生数据、事项表单和工作流工具。

核心研究问题：

1. 如何让 Agent 从学生自然语言中识别事项和办理目标？
2. 如何根据当前事项和流程节点选择必要的知识与工具？
3. 如何将 Agent 生成的建议或草稿安全地转换为工作流操作？
4. 如何用确认、授权、引用、审计与降级控制错误和越权？
5. 相比菜单式工作台，Agent 工作台能否提高事项发现、材料准备和进度查询效率？

## 5. 业务范围

### 5.1 深度实现：请假与销假

覆盖事项咨询、资格与规则说明、对话式填表、材料预审、学生确认提交、辅导员审批、条件触发学院审批、退回修改、撤回、销假和归档。

该流程结构清晰，用于建立第一个端到端 Demo，并验证 Agent 调用工作流工具的安全边界。

### 5.2 重点验证：奖助学金申请

覆盖政策问答、条件初筛、材料清单生成、证明材料一致性检查、申请摘要和评审辅助。系统仅解释和提示资格，不替代正式资格认定与评审。

该场景是 Agent 效果实验的重点，因为其制度依赖和材料复杂度高于请假流程。

### 5.3 模板化业务

- 在读证明、成绩证明等证明申请与盖章；
- 学生活动或场地申请；
- 就业手续与校园办事指南。

这些业务用于验证事项路由和通用工作流模型，不在首版中建设完整专业子系统。

## 6. Agent 能力地图

| 阶段 | Agent 能力 | 调用工具或数据 | 人工控制点 |
| --- | --- | --- | --- |
| 事项发现 | 理解目标、推荐事项、解释办理条件 | 事项目录、制度检索 | 学生选择正式事项 |
| 信息收集 | 多轮追问、复用授权资料、生成表单草稿 | 表单定义、学生基础资料 | 学生检查并确认字段 |
| 提交前 | 检查语义一致性、生成材料清单、提示制度风险 | 校验规则、附件文本、制度条款 | 学生决定修改或提交 |
| 流程中 | 查询状态、解释节点、提醒下一步 | 工作流查询接口、通知服务 | 不允许 Agent 改写流程状态 |
| 审批中 | 摘要申请、整理材料、标出待核验项 | 申请与审批历史 | 辅导员或管理员作决定 |
| 办结后 | 生成摘要、标签和档案建议 | 流程记录、材料清单 | 规则校验或管理员确认 |
| 日常咨询 | 回答学籍、奖助、就业等制度问题 | RAG 知识库 | 显示引用，资料不足时拒答 |

## 7. 系统角色

- 学生：咨询、办理、确认提交、撤回、查询和评价 Agent 建议；
- 辅导员：处理班级或专业范围内的审批和材料核验；
- 学院管理员：处理学院级任务，维护事项、制度和档案；
- 系统管理员：管理账号、角色、工具权限、流程部署和模型配置；
- Agent：系统参与组件，不是拥有独立审批权的业务角色。

## 8. 技术路线

- 前端：Vue 3、TypeScript、Vite、Element Plus、Pinia；
- 后端：Java 21、Spring Boot 3、Spring Security、Spring Data JPA；
- 工作流：Flowable 7、BPMN 2.0；
- 数据库：开发使用 H2，部署与实验使用 PostgreSQL；
- Agent：OpenAI 兼容模型、结构化工具调用、Prompt 版本管理；
- 知识增强：制度文档切分、检索、引用与拒答；
- 测试：JUnit 5、MockMvc、Testcontainers、Vitest；
- 部署：Docker Compose。

首版采用模块化单体。Agent 编排作为独立模块，通过受控服务接口调用事项、知识库和工作流能力，不直接操作数据库或 Flowable 内部表。

## 9. 预期创新点

- 面向校园事务设计“Agent 交互层—工作流执行层”双层协同结构；
- 根据用户目标、事项类型和流程节点动态组装最小必要上下文；
- 使用工具白名单、参数校验、二次确认和审计记录约束 Agent 操作；
- 将事项导航、材料预审、流程解释和制度问答纳入统一任务链；
- 对比传统菜单式工作台与 Agent 工作台，量化任务效率、正确率和用户负担。

这些属于面向具体场景的系统设计与实验验证，不宣称基础模型或 Agent 理论创新。

## 10. 实验设计

### 10.1 事项导航实验

构造学生口语化、信息不完整和多意图表达，评价事项识别准确率、Top-k 召回率、必要澄清率和错误路由率。

### 10.2 对话式办事实验

比较传统菜单填表与 Agent 引导办理，评价任务完成率、完成时间、字段错误数、补交次数和交互轮次。

### 10.3 材料预审实验

构造完整、缺失、矛盾和制度不符样本，评价 Precision、Recall、F1、误报率及学生采纳率。确定性错误与语义问题分别统计。

### 10.4 制度问答实验

比较无检索回答与 RAG 回答，评价答案正确率、引用正确率、知识库外问题拒答率和幻觉率。

### 10.5 工具调用安全实验

测试未确认提交、越权查询、参数篡改、重复调用、提示词注入和模型超时等情况，评价危险动作拦截率、权限校验成功率、审计完整率和降级成功率。

## 11. 实施里程碑
