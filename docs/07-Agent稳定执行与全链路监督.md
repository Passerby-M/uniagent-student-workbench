# UniAgent 稳定执行、审查降级与全链路监督设计

## 1. 设计目标

UniAgent 需要在受控边界内拥有完成校园事务所需的知识和工具权限，同时保证模型判断错误不会直接形成错误业务结果。系统采用以下闭环：

```text
理解意图 → 澄清信息 → 制定计划 → 检索证据 → 选择工具
→ 风险与权限审查 → 用户确认 → 执行 → 结果核验 → 反馈与审计
```

稳定性来自显式状态机、版本化知识、受控工具、分层审查和结果验证，而不是假设大模型每次都能正确推理。

## 2. 稳定完成任务

### 2.1 意图识别

意图结果必须是结构化对象，至少包含事项、动作、目标对象、实体参数、缺失字段、歧义、风险等级和置信度。识别采用三层机制：

1. 事项目录召回：关键词、别名和向量检索返回候选事项；
2. 模型重排与槽位提取：从有限候选中选择并抽取时间、原因等参数；
3. 确定性校验：根据事项 Schema 检查必填字段、类型和业务约束。

置信度不是模型自报分数，而是综合候选差距、字段完整度、规则一致性和上下文一致性形成的门控信号。建议初始策略：

- 低于 0.60：要求重新描述或展示候选事项；
- 0.60—0.80：继续澄清，不调用写工具；
- 高于 0.80：允许规划；
- 只读自动执行可提高到 0.90；
- 写操作无论置信度多高都必须确认。

阈值最终应通过标注验证集校准，不作为固定真理。

### 2.2 最小澄清

系统从事项表单定义读取必填槽位，只询问决定事项、流程分支和工具选择的信息。可以从已授权资料或确定性查询获得的字段不重复询问。连续三轮仍无法消除关键歧义时，展示传统表单或转人工，避免无限对话。

### 2.3 计划—执行—验证

计划由结构化步骤组成，每一步包含目标、前置条件、所需知识、工具、参数、风险、副作用、确认要求、成功判据和失败策略。执行器一次只执行前置条件满足的步骤，模型不能跳过确认和验证节点。

工具返回成功后，验证器至少进行三层判断：

- 接口层：响应码、Schema、超时和错误码；
- 业务层：是否生成申请编号、状态是否变化、对象及字段是否正确；
- 结果层：重新查询正式状态或读取回执，区分请求发送、系统受理和业务完成。

只有结果层满足目标，Agent 任务才进入 `COMPLETED`。无法确认时进入 `PARTIAL_SUCCESS`、`WAITING_EXTERNAL` 或人工核验，不得向用户宣称成功。

### 2.4 状态机

在原任务状态基础上扩充为：

`RECEIVED`、`INTERPRETING`、`NEED_CLARIFICATION`、`PLANNING`、`RETRIEVING_KNOWLEDGE`、`WAITING_CONFIRMATION`、`EXECUTING`、`VERIFYING`、`WAITING_EXTERNAL`、`RETRYING`、`PARTIAL_SUCCESS`、`COMPLETED`、`FAILED`、`HANDOFF`、`CANCELLED`、`EXPIRED`。

状态变化必须由服务端事件触发并记录原因。模型只能提出下一状态建议，不能自行更新业务状态。

## 3. 必要知识与工具

### 3.1 知识版本化

制度知识保存来源部门、原始地址、文档版本、生效和失效时间、适用校区、学院、年级、学生身份、审核人、状态和内容校验值。新版本不覆盖历史版本，每次 Agent 执行记录实际引用的版本。

检索采用关键词与向量混合召回、元数据过滤和重排序。高风险结论必须命中当前有效且适用范围明确的官方制度；历史问答和模型参数知识只能用于帮助检索，不能独立支持资格结论。

证据分级：

- E0：没有证据，只能拒答；
- E1：用户或非官方材料，只作参考；
- E2：官方但时效或范围不明确，仅可低风险解释；
- E3：当前有效且适用的官方制度，可做规则解释和预审；
- E4：E3 加实时业务状态，可支持正式操作前校验；
- E5：制度、实时状态和人工确认一致，可支持高风险操作，但仍需用户确认。

### 3.2 工具注册与发现

每个工具登记唯一 ID、能力标签、输入输出 Schema、前置条件、权限、风险等级、是否有副作用、幂等策略、超时、重试策略、版本、可用状态、负责人和审计等级。

规划器先将任务转换为能力需求，再按能力匹配、权限、风险、版本有效性、历史成功率和当前可用性筛选工具。写操作优先考虑安全和可靠性，而不是速度。具体工具契约见 `06-Agent工具与权限契约.md`。

### 3.3 短期记忆

会话只保存当前任务所需的已确认事实、计划、工具结果和待确认动作。每条事实记录来源、确认状态和有效期。敏感字段任务结束后清除或只保留审计摘要，不形成跨事项的隐式长期画像。

## 4. 分层审查

### 4.1 七道审查门

| 阶段 | 审查内容 | 不通过处理 |
| --- | --- | --- |
| 输入 | 注入、越权请求、恶意文件、敏感数据 | 清理、限制或阻断 |
| 意图 | 事项、动作、对象、参数、置信度 | 澄清或候选选择 |
| 证据 | 来源、版本、范围、直接支持度、冲突 | 拒答或转人工 |
| 工具 | 白名单、Schema、资源范围、业务状态 | 拒绝调用 |
| 写入前 | 服务端预览、风险、后果、确认凭证 | 等待可信确认 |
| 执行后 | 回执、状态、字段、重复记录 | 停止后续并核验 |
| 输出 | 事实、引用、时效、隐私和措辞 | 修正、固定模板或人工 |

输入、制度片段、附件和工具返回都视为不可信数据，不能修改系统指令或权限。工具网关独立鉴权，不接受模型“用户已授权”的陈述。

### 4.2 风险等级

- L0：公开信息解释，可自动处理；
- L1：本人普通只读查询，鉴权后自动处理；
- L2：奖助、学籍等权益相关判断，需要有效证据和明确免责声明；
- L3：正式提交、撤回等状态变更，必须预览和二次确认；
- L4：越权、不可恢复删除或代替人工作重大决定，禁止自动执行。

## 5. 降级与兜底

### 5.1 失败分类

- 可重试：网络超时、限流和临时服务故障；
- 模型质量：意图低置信、结构化输出错误、事实核验失败；
- 证据不足：未找到制度、制度过期或冲突；
- 权限失败：未登录、会话失效、资源不属于用户；
- 业务拒绝：截止时间、条件不符、状态不允许；
- 状态未知：接口成功但无法查询正式结果；
- 安全失败：提示词注入、越权、批量导出和恶意文件。

权限、业务拒绝和安全失败不得通过换模型或重复调用绕过。写入结果未知时，必须先查询真实状态，禁止直接重试。

### 5.2 降级顺序

```text
正常模型 → 有限重试 → 备用模型 → 规则模式
→ 只读模式 → 人工接管 → 传统官方入口
```

- 意图不明确：追问或展示候选，不调用工具；
- 模型不可用：使用事项搜索、规则校验和传统表单；
- RAG 无证据：明确拒答，提供制度入口或人工渠道；
- 写工具失败：按幂等键查询结果，不直接重交；
- 状态冲突：冻结后续写操作，创建异常记录并人工核验；
- 安全命中：立即阻断并记录安全事件。

### 5.3 熔断

模型、检索源、业务工具和具体事项分别维护 `CLOSED`、`OPEN`、`HALF_OPEN` 状态。连续超时、错误率升高、状态不一致或制度版本待审核时打开熔断，只保留只读说明与传统入口。恢复需要连续探测成功、状态一致、制度版本确认和低风险灰度验证。

## 6. 全业务监督与追溯

### 6.1 统一标识

采用一个根关联 ID 加各阶段实体 ID：

- `correlation_id`：一次端到端业务动作；
- `request_id`、`trace_id`、`span_id`：请求与技术链路；
- `session_id`、`agent_run_id`、`llm_call_id`、`rag_query_id`、`tool_call_id`：Agent 链路；
- `transaction_id`、`application_id`、`application_no`：业务事务；
- `business_key`、`process_instance_id`、`task_id`：Flowable 链路；
- `confirmation_id`、`approval_id`、`notification_id`、`archive_id`：关键业务环节；
- `event_id`：不可变审计事件。

关联链为：

```text
session → agent_run → LLM/RAG/tool → transaction → application
→ business_key → process_instance → task → approval → notification/archive
```

传统页面入口没有 Agent ID，但仍通过 `request → transaction → application → process` 完成追踪。

### 6.2 统一事件账本

关键事件使用统一信封，记录事件类型、版本、发生和入库时间、来源模块、结果、关联 ID、脱敏操作者、资源及版本、状态变化和安全错误码。

事件覆盖：

- Agent 状态、LLM、RAG、工具授权和执行；
- 用户确认的签发、消费和失效；
- 草稿、提交、退回、重提、撤回、生效、销假和归档；
- Flowable 流程与任务的创建、完成、中断和结束；
- 人工审批、通知投递和一致性巡检。

审计事件不可更新或删除；错误通过新增纠正事件处理。关键业务变更与事务 Outbox 在同一数据库事务写入，避免“业务成功但审计缺失”。

### 6.3 Trace、指标和日志分工

- 审计事件回答“谁在何时基于什么执行了什么，结果是什么”，不可采样；
- OpenTelemetry Trace 回答“请求在哪个组件耗时或失败”，普通链路可采样；
- 指标与告警回答“系统是否正在发生普遍问题”；
- 应用日志仅用于安全排错，不承担业务事实证明。

关键指标包括意图澄清率、工具调用成功率、模型超时率、RAG 无证据率、危险调用拦截率、流程启动失败率、超时待办数、状态不一致数、通知失败率和归档失败率。

### 6.4 一致性巡检

定时巡检以下不变量：

- `IN_REVIEW` 必须对应运行中的流程和当前用户任务；
- `RETURNED` 必须对应学生修改任务；
- `EFFECTIVE` 必须对应等待销假消息；
- `CANCELLATION_PENDING` 必须对应销假确认任务；
- `ARCHIVED` 必须对应已结束流程和归档记录；
- 每个流程实例、确认凭证和人工审批记录均能关联唯一业务申请。

巡检只报告异常并创建定位记录，不允许 Agent 自动修改 Flowable 或业务状态。

### 6.5 单申请时间线与故障定位

管理端可用申请编号重建统一时间线：学生会话、Agent 决策、制度版本、工具授权、用户确认、业务事务、流程节点、人工审批、通知和归档按时间排序展示。

故障定位顺序：

1. 用 `application_no` 找到 `correlation_id` 和 `process_instance_id`；
2. 查看事件账本确定最后成功环节；
3. 使用 `trace_id` 定位技术失败 Span；
4. 核对业务状态与 Flowable 当前节点；
5. 检查确认、幂等和审批记录；
6. 根据错误分类决定重试、补偿、人工处理或保持冻结。

## 7. 数据保护与保留

普通日志和 Trace 不保存 Prompt、附件全文、令牌、身份证号、健康及家庭经济信息。审计只存必要字段、参数摘要哈希和制度引用。不同数据按公开、内部、个人和敏感个人信息分级，设置差异化查询权限与保留周期。

本科原型可采用 PostgreSQL 审计表、事务 Outbox、Spring 过滤器 MDC、Micrometer/OpenTelemetry、Flowable 监听器和定时一致性巡检，不需要引入 Kafka 或专用日志集群。

## 8. 可量化验收

- 越权读写和缺确认写操作拦截率：100%；
- 高风险写操作确认覆盖率：100%；
- 已执行写操作的状态核验覆盖率：100%；
- 核心事件审计完整率：100%；
- 单申请可从编号重建完整关键时间线；
- Agent 故障时请假/销假传统流程可用率：100%；
- 状态一致性测试集中的异常发现率：100%；
- 注入测试中的危险工具执行数：0；
- 知识库无证据问题不输出确定性制度结论；
- 所有最终制度结论能定位到文档版本和条款片段。
